# 審查判準

只讀這次適用的段落。呼叫方的已核准需求與領域規則優先；下列是起點，不是要求所有工作填滿模板。

## 派工單／需求與計畫

- 另一個 agent 能否從文件辨識目標、輸入、交付物與驗收方式？不同合理解讀是否會做出不同產品？
- 需求、計畫、任務與驗收有沒有矛盾或必要遺漏？分清「文件真的矛盾」「需要負責人決定」與「reviewer 想加的新功能」。
- 哪些現有行為必須保留？改動會碰到哪些相容性、資料、背景執行或失敗路徑？沒有依據時不能發明需求。
- 執行位置、版本、依賴、授權、停止／恢復與回報是否足以交接？沿用已確認資訊，不重開訪談。
- 驗收是否能觀察結果，且不只是實作動作或自我宣告？無法自動驗證的部分明列人工驗收／未驗證，不能假造綠燈。
- 範圍和優先序能否讓執行者收斂？非必要的改善不當成 blocker。缺陷需指出具體失敗情境，不能用「可能不夠完整」要求無限補細節。
- 私有派工單所需的機器／路徑等操作資訊可保留；真實 credential 應引用安全來源。公開／分享輸出另查洩漏，不把私有文件硬改到無法執行。

## 程式實作後

- 依指定 base/head 與需求檢查行為；找本次引入或與本次交付直接相關的缺陷，其他真問題另記。
- 每個問題給可到達的觸發條件、實際控制／資料路徑和影響；不以未經支持的假設建立 blocker。
- 檢查原本正常的功能、相容性、資料保存、失敗／重試／並行與背景生命週期。依變更挑相關路徑，不列無關通用清單。
- 測試綠燈只能證明實際覆蓋的路徑。必要時讀呼叫端與測試前置條件，區分手動調用成功、真實啟動、實機與正式環境證據。
- 修法是否讓主目標失焦、擴大變更或破壞其他行為？提出必要回歸驗證；不要替成立的問題硬背書第一個修法。
- 格式、lint、自動工具已涵蓋的小事不反覆評論；沒有實際影響的重構／品味建議不能阻擋交付。

### 從內建 review 採用的回報紀律

以下參考本機實際檢視的 **Codex CLI 0.164.0 內建 review prompt**，以及 [Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)、[Custom Code Review rules](https://developers.openai.com/blog/custom-code-review-rules-for-codex)（2026-10-29 查核）。這是採用判準，不是聲稱雙 agent 流程為內建功能。

- 問題必須具體、可採取行動，影響正確性、效能、安全或有實際代價的可維護性；要求的嚴謹度符合專案用途。
- 聲稱會破壞其他地方時，指出實際受影響的呼叫端／契約，不能只猜。既有問題與本次新增問題分開標示。
- 一個獨立問題一條意見，重複合併保留來源。程式 finding 優先定位變更中的最小相關行段，說明通常一段即可。
- 依影響排序；P0 為普遍且立即阻擋的重大故障，P1 緊急，P2 一般缺陷，P3 低影響。需要特定條件時明說，不把嚴重度與是否這次必修混為一談。
- 使用適用範圍的 repo 規則，引用真正支撐 finding 的規則位置；普通程式缺陷不需要硬湊規則。規則也要保留合法例外，機械檢查留給工具。

不照搬內建 JSON 輸出或二選一的整體 correctness 結論：本流程還要承載待決與證據不足。也不因作者有意這樣做就認定安全，或把「作者會喜歡」當採納依據。沒有 findings 時照實回報，仍列測試缺口；agent 自評信心不是經校準的正確率。
