# 文件對齊判準

## 證據如何支持敘述

| 文件聲明 | 查核依據 | 不足以單獨證明 |
|---|---|---|
| 目前程式的行為、參數、預設值 | 當前實作、實際呼叫鏈、適用設定與版本 | 設計文件、舊 commit、測試名稱 |
| 已驗證、測試通過 | 對應版本的既有執行結果與驗證範圍 | 測試檔存在、過去不同版本的綠燈 |
| 已部署、服務已採用新行為 | 既有部署紀錄與可唯讀確認的執行版本／設定 | 本機 HEAD、合併完成、原始碼已修改 |
| 已送達、真人驗收成功 | 原流程的回執或實際驗收紀錄 | queued、服務存活、模擬測試通過 |
| 跨 repo 的整合行為 | 呼叫方與被呼叫方的介面、版本、設定及必要既有紀錄 | 只看其中一邊的 README |

原則：文件跟上實作，但實作不自動等於已部署。標清觀察的 repo／commit／環境；跨 repo 版本不匹配、未提交修改與本機／線上差異要明列。優先用既有可追溯證據，不為取得證據去變更系統。

若只能確認程式能力，就描述「程式目前支援……」，不要升格成「正式環境已啟用」。既有「已部署」敘述找不到足夠證據時，不逕行判定未部署；保留歷史敘述並註明本次能確認與不能確認的範圍。

## 全 repo 查核要覆蓋什麼

從目錄與文件清單建立覆蓋圖，逐區閱讀維護中的文件，再追相關實作：入口與索引、安裝／操作、架構與資料流、介面／設定／預設值、測試／部署／維運說明，以及規格與歷史記錄。存在才查，不為湊種類建檔。除程式碼外，腳本、workflow、服務啟動方式與設定來源也可能是行為依據。

整個 repo 看過一遍不等於逐行閱讀依賴或產物；可排除 vendor、build、cache、原始附件等非維護來源，但列出排除範圍。沒有讀到、不能存取或來不及核對的區域屬覆蓋缺口，不能以抽樣代替全庫完成。

Git 紀錄用來定位 hotfix 與解釋差異；查核仍回到目前內容。不要把歷史規格中的未完成項目自動勾選成完成。

## 觸發範圍要覆蓋什麼

觸發範圍的覆蓋是「所有引用到觸發事件的地方」，不是「最近改過的檔案」。

1. **列搜尋鍵。** 從觸發事件推出所有可能被文件引用的寫法：完整路徑與其下的子路徑、單獨出現的檔名或目錄名、符號／參數／指令／設定鍵名稱，改名時舊名與新名都要。也搜文件常用的相對寫法（例如只寫 `output/` 底下的子目錄名）。
2. **全 repo 搜。** 用搜尋鍵掃整個 repo 的維護文件，不限於近期 diff 碰過的檔；依賴、快取、產物照全庫規則排除並列出。
3. **逐條核對目標。** 每條命中引用都要確認它指的東西現在的狀態。只核對路徑前綴會漏掉「上層目錄還在、文件指到的子檔已經不在」或反過來的情況。
4. **不可逆的結論要多查一層。** 要寫「已刪除且無法還原」「從未進版控」這類結論前，查 git 歷史（所有分支，以及已知的備份來源，例如封存的分支包）；查不到就寫「本次未找到副本」並列出查過哪些來源，不直接寫無法還原。
5. **類型判斷不變。** 命中的文件照下一節判斷是現況文件還是歷史紀錄，再決定直接改或加註。
6. **守住邊界。** 範圍外看到的其他落差記成範圍外發現回報，不順手修。回報寫明觸發事件、搜尋鍵與命中清單，讓讀者知道這不是全庫對齊。

## 怎麼修改不同文件

先認定文件類型。只有文件本身（標題、開頭說明或狀態欄位）標明是歷史紀錄、已結案或 ADR，才照下方「歷史／已結案文件、ADR」處理；其他一律當現況文件，直接改內文（需求／AC 與驗收腳本的預期仍不改）。日期、檔名、所在目錄或內容看起來舊都不算標明，拿不準時也當現況文件。

- **現況文件**：修正錯誤行為、介面、命令、路徑、預設值與圖表；必要時補一小段漏掉的行為說明，保留既有章節與格式。不無故重寫或做語氣整理。
- **現況操作手冊／驗收腳本**：手冊寫對應版本實際可用步驟，已知缺陷明列限制與工程待辦，不把暫時替代路徑升格成正式需求。依已核准需求／AC 寫的驗收腳本保留預期，可註記差異，不能改預期替缺陷背書；兩種文件不可互當正本。
- **歷史／已結案文件、ADR**：保留原文、原結論與當時狀態，在頂部或衝突處鄰近加清楚區隔的現況註記，標查核日期、目前差異及證據。有已存在的新決策或取代文件就連到它，不替 user 發明新決策。ADR 註記不是改決策或取代狀態；需要新決策時回原流程，不靠註記批准。
- **純未來計畫**（文件本身標明是計畫、提案或待辦）：未實作本來就是計畫的性質，不把它改成目前行為；只有它被誤讀成現況、或與實作的差異有必要說明時才加註。
- **引用與索引**：隨修訂同步現有入口、連結、圖表與雙語版本，避免單頁修好而摘要仍舊。生成內容不手改；需要生成時先查清副作用，不能確認安全則回報待辦。
- **其他 repo**：查其規範、介面與必要實作，回報它的文件落差；授權前不建立報告檔、加註、commit 或修改其任何文件。

歷史加註例（沿用 repo 自己的語系與註記格式）：

> 現況註記（YYYY-MM-DD）：本段保留當時設計；目前 `src/example.ts` 的 `retryLimit` 已改為 2。依據：commit `abcdef0`，`src/example.ts:42`。本次未查證正式環境版本。

## 無法對齊時

程式、設定與既有驗證互相矛盾時，先釐清適用版本與條件；仍不能確認就記錄具體衝突與缺少的證據，不猜測、不改程式，也不把未知寫成已驗證。其餘不依賴該疑點的文件可繼續修訂。

差異可能涉及 bug 或未核准的需求時，可描述已觀察到的現況並保留原需求／歷史規格，明列兩者不符；不要透過改規格、驗收結果或狀態欄，替程式補出「符合需求」的結論。

完成判準是新敘述能由實際依據支持、授權範圍內的文件互相一致、歷史未遭覆寫，而且覆蓋缺口與外 repo 待辦沒有被隱藏。文件檢查成功不等於產品 QA 或部署驗收成功。
